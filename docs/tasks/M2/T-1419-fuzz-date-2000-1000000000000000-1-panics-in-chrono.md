## Goal
`=DATE(2000,1000000000000000,1)` (and the fuzz input it was reduced from) never panics, in debug
or release builds, and gives Excel's result.

## Context
Nightly fuzz run 38202077837 (2026-10-12, `main` eba0eb0), target `formula_eval`, artifact
`crash-4b2019ed857398b25cdaa4849fc516c0682bde71`. The input is the 74 bytes
`(((0.2+Data!C5)+DATE(Data!B8,1000000000000000.0,1))+DAYS360(Data!B3,0.2)%)`; the target sets
it as `=...` in `C3` of its small model (`fuzz/fuzz_targets/formula_eval.rs`). Reproduced by the
steward on 1337fe2 with a debug test through the facade (`Workbook::set`, then
`Workbook::value`):

    panicked at crates/rustsheet-engine/src/formatter/dates.rs:167:20:
    `NaiveDate + Months` out of range

This is a chrono panic, not a debug_assert, so release builds abort too (directive 5).
Narrowed: `=DATE(2000,1000000000000000,1)` and `=DATE(0,1000000000000000,1)` panic alone.
`permissive_date_to_serial_number` adds `Months::new(abs_month)` with the unchecked `+`/`-`
operators; a month that saturates near `i32::MAX` overflows chrono's range. Use
`checked_add_months`/`checked_sub_months` (as `financial_bonds.rs` does) and return the
out-of-range error. Excel's result for huge month (and day) arguments must come from evidence:
look for existing DATE probes first, otherwise use the excel-probe skill. While there, check the
other unchecked `+ Months`/`- Months` sites reachable from formulas
(`date_and_time.rs` DATEDIF "MD", `conditional_formatting.rs`) and fix any that a formula can push
out of range.

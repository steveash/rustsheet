## Goal
`make mark-ready` works from a Claude Code session: a marker comment that the session's GitHub write path ends with
its attribution footer still verifies, and the verify still refuses anything else after the marker.

## Context
- In this session environment, every comment written through `gh api` or the GitHub MCP tools gets the attribution
  footer appended: a blank line, `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`. That holds
  even when the script's own body has no footer.
- `merge_ready.parse_marker` (scripts/merge_ready.py) requires the marker block to end the comment. So the
  verify step right after posting fails with `V1 (unlabel): malformed marker: no complete marker block at the end
  of the comment`, for example on #2353 (T-3076, comment 6509849730). On #2348 (T-2949), a worker got around it by
  posting a second marker and editing the footer out (comments 6509268424 and 6509272858).
- The marker is an anti-forgery record (SPEC-0027 section 2), so the tolerance must be exact. Strip only that one
  footer, verbatim and only at the very end, before parsing. Any other trailing text stays a refusal.

## Acceptance criteria
- [ ] `parse_marker` accepts a marker followed by exactly the footer above (with or without a trailing newline). It
      still refuses any other text after the marker, a footer with extra text, and a footer before the marker.
- [ ] `scripts/test_merge_ready.py` covers each case; SPEC-0027 section 2 names the allowed footer.
- [ ] `make check` green; reviewers approve.

## Out of scope
- Changing what the session appends to comments.

## Outcome
Most of this already landed with T-3164 (`without_footer`, tests, SPEC-0027 section 2 wording). Added the
remaining case: a footer followed by a trailing newline is accepted (`rstrip("\n")` before stripping the
footer), with a test. Anything else after the marker is still refused. No eval change.

## Goal
A readiness marker written by `make mark-ready` from an agent session verifies (`make merge-ready-verify` exit 0), so
shadow and train runs see the PRs workers mark ready.

## Context
- Found 2026-10-29 on the first live mark after T-2989 set `shadow`: `make mark-ready PR=2337 REVIEW=...` posted
  the marker comment and the `ready-to-merge` label, then its own read-back failed with
  `V1 (unlabel): malformed marker: no complete marker block at the end of the comment` (exit 2).
- Cause: the session's GitHub write path appends the attribution footer after the body
  (`\n\n---\n_Generated by [Claude Code](https://claude.ai/code)_`), so the `<!-- merge-train-ready v1 ... -->` block
  no longer ends the comment. `parse_marker` (`scripts/merge_ready.py`) requires it to. The same is likely true of
  the merger's `merge-train-ejected v1` blocks and of step-mode comments posted with the MCP tools.
- Until fixed, every session marker reads as malformed: the shadow merger has no candidates (T-2991's evidence
  cannot accrue), and in `train` mode the merger would unlabel every PR.
- Options: accept that one footer (exact shape, at most once) after the closing `-->`; or put the generated footer
  in the body before the block so the server does not append one (the server strips duplicate footers). Keep V1's
  author rule unchanged.

## Acceptance criteria
- [ ] `parse_marker` accepts a marker followed by the attribution footer and still rejects any other trailing
      text; unit tests in `scripts/test_merge_ready.py` cover both, and the ejection block if it shares the rule.
- [ ] `make merge-ready-verify PR=<n>` exits 0 on a PR marked from a session (re-mark #2337's shape or a new PR).
- [ ] Decision record (protected path); architecture and security approve.
- [ ] `make check` green; reviewers approve.

## Out of scope
- Changing the footer itself, which the platform adds.

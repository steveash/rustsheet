## Goal
A routine session can perform the merge train's GitHub writes safely: the script decides every write, the session
only carries it out with the GitHub MCP tools, and the script checks the result.

## Context
Split out of T-2995 (its fourth criterion). T-3001's probe (SPEC-0027 section 4, "T-3001's probe", 2026-10-28)
found that a routine session's `gh api` comment, label and unlabel writes are refused by the tool-permission
layer, while the GitHub MCP tools write. So the step mode is needed (SPEC-0027 section 4, "GitHub access"):
- the script prints the next write as one JSON action from a closed enum (`merge`, `label`, `unlabel`,
  `comment`), and fills every field itself: PR numbers validated as integers the script selected, label names
  from a fixed list (`ready-to-merge`, `merge-train-ejected`), comment bodies generated in full, and
  `expectedHeadSha` for merges;
- the session performs exactly that action and runs the script again; the script reads GitHub's state back and
  aborts on any difference from the expected result;
- the session never adds, skips, reorders or changes an action;
- T-2986's minimal fallback uses the same schema.
- T-3055 (decision 0165) added writes the enum must also carry: removing `merge-train-stop` from a PR that is
  not a flip, opening the revert PR and the task-only PR (`create_pull`, title, head and body generated by the
  script), and deleting a merged PR's branch (`delete_branch`).

## Acceptance criteria
- [x] The step mode is built on `scripts/merge_train.py`'s single write path, with the action schema
      validated on output and the read-back checked on the next run.
- [x] Tests cover each action type, a read-back that differs (abort), and an action the session did not
      perform (abort, nothing skipped).
- [x] `make check` green; reviewers approve.

## Out of scope
- Routine prompts (T-2996). Shadow mode (T-2995). Stats (T-3076).

## Outcome
- `scripts/merge_step.py` (decision 0169): the action schema (`comment`, `label`, `unlabel`, `merge`,
  `create_pull`, `delete_branch`, `dispatch`; exact fields; the three train labels; gh_client's bounds),
  `StepClient` (reads through the real client; each of the seven writes is one action between a read of the
  state it changes and the read-back of that state; any other non-GET request is refused), and the ack file
  (`make merge-train-ack SEQ=<n> [REFUSED=1]`). `make mark-ready STEP=1` validates its actions with the same
  schema.
- `make merge-train TRAIN=1 STEP=1` / `SHADOW=1 STEP=1`: the run keeps its lock and in-memory state, prints each
  action and waits for the ack. Done must read back exactly; refused must read back unchanged and then fails as
  a direct write would (a refused squash stops, a refused branch deletion is logged); no ack in 10 min, an ack
  for another `seq`, or any other read-back aborts (`StepError`, exit 2, lock released).
- `scripts/test_merge_step.py` (15 tests): every action type validates and malformed ones are refused; each write
  read back; a read-back that differs (wrong label set, other body, an outsider's comment, another squash
  message) aborts; an action acked but not performed aborts; a refused write; no write bypasses the actions; the
  ack file (wrong `seq`, timeout, forged ack); a whole green train merged through actions on test_merge_train's
  simulator, a refused branch deletion, and an unperformed merge that aborts with the lock released.
- SPEC-0027 section 4 "GitHub access" has an "As built" note. Follow-up: T-3190 (routines.md merger prompt).
- Eval delta: none (scripts and docs only).

## Goal
A readiness marker written by `make mark-ready` is read back as well-formed by V1, so a PR the
steward or a worker marks ready stays ready instead of being unlabelled on the spot.

## Context
On #2343 (the 2026-10-29 18:47 UTC steward PR, `shadow` mode) `make mark-ready PR=2343 REVIEW=...`
posted its marker comment, then failed: `V1 (unlabel): malformed marker: no complete marker block
at the end of the comment`. The posted comment (id 6506549701) ends with the `-->` of the marker
block followed by a blank line, `---` and `_Generated by [Claude Code](https://claude.ai/code)_`:
the GitHub posting path in these sessions appends that attribution footer to every comment.
`scripts/merge_ready.py` `parse_marker` takes everything after the last `MARKER_OPEN` and requires
exactly the marker's lines, so any trailing text fails it. In `train` mode no PR could then be
marked ready. Fix on the reading side (accept trailing text after `MARKER_CLOSE`, or only a known
footer) and keep the writer's own body unchanged; add a unit test with the footer appended. Check
whether `scripts/gh_client.py` is the path that posted it and whether other comment readers
(merge-train stop label, revert PR, intake) parse a block "at the end" the same way.
`scripts/` is a protected path: decision record plus reviewer-architecture and reviewer-security
approval. Filed by the 2026-10-29 18:47 UTC steward run.

## Acceptance criteria
- [ ] A marker comment with the attribution footer after `-->` parses; one with text between the
      block's lines still fails.
- [ ] `make mark-ready` on a green, approved PR leaves it labelled and reports it ready.
- [ ] `make check` green; reviewers approve.

## Out of scope
- Changing what the posting tool appends.

## Outcome (dropped, 2026-10-30, T-3164)
Duplicate of T-3164, which fixes the same failure on the reading side (decision 0172): `parse_marker` accepts
exactly one trailing attribution footer and still rejects any other trailing text. Other comment readers checked:
no other script parses a block at the end of a comment (the `merge-train-ejected v1` block is written by the
merger and never parsed; the stop label and revert PRs are read by label and title, not by comment body).
The live `make mark-ready` check is on T-3164's PR.
